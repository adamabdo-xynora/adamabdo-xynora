# Adam Abdo

Cofounder of [Xynora](https://xynora.com), a B2B AI practice. I build production systems with Claude Code daily. Two of them are closed-source client systems running in production today: a quoting and estimation platform for a manufacturing business, and a webhook-driven integration layer that syncs data between vendor systems. The patterns I can share publicly, I do — starting with [webhook-guard](https://github.com/adamabdo-xynora/webhook-guard), a security-hardened webhook receiver extracted from that production work: HMAC verification, idempotent delivery, and credential redaction by value before anything touches disk.

The evaluation side of that work is public too: [agent-eval-harness](https://github.com/adamabdo-xynora/agent-eval-harness) calibrates an LLM judge against human-labeled transcripts — Cohen's kappa, per-criterion drift gates, and a six-run calibration log that includes the judge catching an arithmetic error in my own ground-truth labels.

The agent-authorization side is public as well: [mcp-capability-guard](https://github.com/adamabdo-xynora/mcp-capability-guard) is an MCP server where every write needs a warrant — single-use capability tokens bound to one exact mutation, human confirmation for destructive operations, and a data-layer floor that refuses do-not-contact writes even when every layer above has said yes. Extracted from a production CRM agent; run `npm run demo` to watch five attacks meet their typed refusals.

And the retrieval side: [rag-receipts](https://github.com/adamabdo-xynora/rag-receipts) is RAG you can audit — every claim carries a citation and a verbatim quote, both verified in code against the chunks the model was actually shown, and the system refuses when the corpus can't answer rather than writing something fluent. The eval gate scores a correct refusal as a pass and names a fluent answer to an unanswerable question as the headline failure. The similarity floor is a measured constant rather than a tuned one: calibration against live `voyage-4` embeddings put every required chunk above 0.5106 and every chunk any unanswerable question retrieves below 0.3622, and the committed run doc records the derivation along with the fact that the previous guess sat below that ceiling — trap material was reaching the generator until the measurement caught it.

And the compliance side, in Python: [suitability-receipts](https://github.com/adamabdo-xynora/suitability-receipts) decides whether an investment recommendation is suitable for a documented client, and refuses rather than producing a determination it cannot trace to documented facts. The type system does the enforcing: a supported determination cannot be constructed unless it records a passing check for every rule in the taxonomy, each citing a documented profile factor a verifier can recompute rather than trust. Its 35-case eval set — every expectation derived by reading the inputs, never by running the engine — found a defect the test suite missed: two rules ignored the recommendation's action, so a sell that strictly reduced the exposure being refused for was refused anyway. I committed the disagreement as the finding, then fixed it in a separate commit that distinguishes a breach the recommendation created from one it inherited and reduced, without letting the reducing case silently pass.

All five ship a multi-stage Dockerfile whose test stage runs the real suite inside the image — 334, 240, 158, 104, and 68 tests respectively, 904 in total, every one of them offline — while the runtime stage drops its dev dependencies and cannot run the test tooling at all. No credential can reach a layer: each `.dockerignore` keeps it out of the build context, and keys arrive only through `docker run`.

All five publish a versioned container image to GHCR from CI, on a version tag. The workflow is a gate rather than a build. Every `test` stage ends at `CMD`, which runs nothing during `docker build` — in two of the five that means a `--target test` build proves literally nothing, and in the other three it proves lint and types but not one test — so a workflow that built the test stage and called it a gate would publish untested images while reporting green. Instead the suite, the typecheck, and each repo's eval or demo are run with `docker run`, each as its own step with no pipe and no `|| true`, and the push step is ordered after all of them. The only credential involved is the built-in `GITHUB_TOKEN`, scoped to `contents: read` and `packages: write`, plus `id-token: write` and `attestations: write` on that one job so it can sign what it publishes. Each image is public, tagged with both the version and the commit, built for `linux/amd64` and `linux/arm64`, and carries SLSA v1 build provenance binding its digest to the workflow run and commit that produced it — `gh attestation verify oci://ghcr.io/adamabdo-xynora/<repo>:0.1.1 --owner adamabdo-xynora` returns 0 for all five, and returns 1 against a wrong owner. `v0.1.0` is also still published for each, amd64-only and unsigned, at the digest it has always had: closing the arm64 gap meant cutting `v0.1.1`, not retagging bytes someone may already have pulled.
